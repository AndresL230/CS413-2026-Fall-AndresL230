# LAMBDA workbench

A local web front-end for the LAMBDA language tools, built with
Model–View–Controller. You load or type a program, apply it, and run Lint,
Interpret, Type-check or Compile on it. Results appear as text on the page.

- Design: [ARCHITECTURE.md](ARCHITECTURE.md)
- Tests and browser results: [TESTING.md](TESTING.md)
- AI use: [AI-TRANSCRIPT.md](AI-TRANSCRIPT.md)

## Requirements

- Python 3.12 or later. Tested with Python 3.13.13 and 3.14.7 on Linux.
- Flask 3 (tested with 3.1.3), installed by the commands below. There are no
  other dependencies.
- A current browser. Tested with Chrome 154.

## Setup

From this directory (`assigns/04/MySolution`):

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

On Windows, use `.venv\Scripts\python` in place of `.venv/bin/python`.

## Start

```sh
.venv/bin/python app.py
```

Then open <http://127.0.0.1:8413/>. The server listens only on the loopback
interface. Stop it with Ctrl+C.

Options: `--port 8500` changes the port, and `--timeout 10` changes the time
allowed for one Lint or Interpret run (default 5 seconds).

## Tests

```sh
.venv/bin/python -m unittest discover -s tests -t .
```

This runs 109 tests in about two seconds. See [TESTING.md](TESTING.md).

## Demonstration

Sample inputs are in [`examples/`](examples).

**1. Factorial and Fibonacci.** In **Load source**, choose **Factorial
(canned)** and press **Load**. The page shows "Applied source: Factorial
(canned), revision 1". Press **Interpret**; the result is `D0Vint(arg1=120)`.
Load **Fibonacci (canned)** the same way. It becomes revision 2, the earlier
result is cleared, and Interpret gives `D0Vint(arg1=55)`.

**2. An undeclared variable.** Choose **Manual input** and press **Load**.
Type `D0Evar("x")` and press **Apply changes**. Press **Lint**; the result is
"Lint error: Undeclared variable(s): x". Now change the editor text to
`D0Elam("x", D0Evar("x"))`. While the edit is unapplied, the action buttons
and the Load menu are disabled. Press **Apply changes**, then **Lint**; the
result is "No free variables found."

**3. Lint passes, Interpret fails.** Load `examples/division-by-zero.lambda`
with **Choose File…**, or type `D0Eop2("/", D0Eint(1), D0Eint(0))` and apply
it. **Lint** succeeds, because the expression has no free variables.
**Interpret** reports "Runtime error: division by zero". Lint only checks that
every variable is bound. It does not run the program, so it cannot tell
whether running it will succeed.

**4. Placeholders and Execute.** With any source applied, **Type-check**
reports "Type checking is not yet implemented." and **Compile** reports
"Compilation is not yet implemented." Both are shown as "Not implemented",
not as success. **Execute** is disabled, and the note under the buttons
explains that it runs code generated by Compile and no generated code exists.

**5. A program that does not finish in time.** Load
`examples/slow-fibonacci.lambda` and press **Interpret**. The status shows
"Working: Interpret is running…" and the controls are disabled. After 5
seconds the result is "Timed out", the controls return, and the source is
unchanged.

## Input format

The source is one Python constructor expression of type `d0exp`, for example:

```python
# 20 + 22
D0Eop2("+", D0Eint(20), D0Eint(22))
```

- Constructors: `D0Eint(int)`, `D0Ebtf(bool)`, `D0Eop1(name, e)`,
  `D0Eop2(name, e1, e2)`, `D0Evar(name)`, `D0Elam(x, body)`,
  `D0Efix(f, x, body)`, `D0Eapp(e1, e2)`, `D0Eif0(test, then, else)`,
  `D0Elet(x, e1, e2)`, `D0Epair(e1, e2)`, `D0Epfst(e)`, `D0Epsnd(e)`.
- Names and operators are string literals. Integers are integer literals,
  optionally negative. Booleans are `True` or `False`.
- Nesting, `#` comments, line breaks and trailing commas are allowed.
  Arguments may also be given by field name, as in `D0Eint(arg1=5)`.
- Operators supported by the interpreter: `+1` and `-1` for `D0Eop1`;
  `+ - * / < > <= >= == !=` for `D0Eop2`. `/` is integer division.
- `D0Eif0` expects a boolean test, such as `D0Eop2("<=", D0Evar("n"), D0Eint(0))`.

The text is never executed as Python. It is parsed, and a reader accepts only
these constructor calls with arguments of the right type. Anything else, such
as `import os` or `print("hi")`, is reported as an input error with its line
and column.

## Execution bounds

| Bound | Value | Where |
| --- | --- | --- |
| Source size | 65,536 bytes of UTF-8 | `MAX_SOURCE_BYTES` in `lambda_workbench/model.py` |
| Upload request size | 1 MiB | `MAX_REQUEST_BYTES` in `lambda_workbench/web.py` |
| Time for one Lint or Interpret | 5 seconds (`--timeout`) | `lambda_workbench/backend.py` |
| Interpreter recursion depth | 50,000 Python frames | `lambda_workbench/tool_worker.py` |
| Worker memory | 2 GiB address space, where the platform supports it | `lambda_workbench/tool_worker.py` |
| Displayed value length | 20,000 characters, then truncated | `lambda_workbench/tools.py` |
| Results kept per revision | 20 | `MAX_RESULTS` in `lambda_workbench/model.py` |

Lint and Interpret run in a separate worker process. When the time limit
passes, the worker is stopped and the result is "Timed out". A program that
recurses without end usually reaches the recursion limit first and is
reported as a runtime error instead.

## Known limitations

- Single user. All browser tabs share one workbench. State is held in memory
  and is lost when the server stops.
- There is no Stop button. A slow run ends only at the time limit.
- The reader checks argument types but not operator names. An unknown
  operator such as `D0Eop2("%", ...)` passes Lint and fails in Interpret.
- Applying an edit keeps the source name. An edited example is still shown as
  "Factorial (canned)" with a higher revision number.
- The memory limit is not applied on Windows. The time limit still is.
- Integers longer than Python's print limit (4,300 digits) are computed but
  shown as "too large to display".
- The server is Flask's development server, which is suitable only for local
  use.
- Type-check, Compile and Execute are placeholders.

## Reflection

MVC helped most with the state rules. Things like “a rejected change keeps the previous source” and “every accepted change is a new revision and clears the results” ended up as a few methods on one model class, with no HTTP or HTML in it. That meant I could test them directly and fast, and the tests read pretty close to the requirement table. The backend boundary helped the same way. The controller only knows the five operations and a result type, so for the busy and failure tests I could swap in a fake backend that blocks or throws when I want it to.

The editor was the hardest part to keep separated. The “no actions while there are unapplied edits” rule belongs in the model, but the page has to grey out the buttons as soon as the user types, before any request goes out. So the browser ends up doing the same comparison the model does. The server still has the final say, but it’s real duplication. Long-running work was the other tricky spot. Each operation is split into “begin” and “finish” in the model, with the slow call happening in the controller in between, so the controller has to make sure it always calls finish.

The change this setup makes easiest is plugging in a real compiler. The model already stores a generated-code artifact for each revision and throws it out when the source changes, and Execute already gets that artifact. A compiler would go inside the backend adapter, and the model, controller and page wouldn’t have to change.
